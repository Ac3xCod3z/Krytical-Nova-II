# M5.2 NavWorld spike: report (6 Nov 2026)

Throwaway code, Editor only, Zone01_StarterTown's baked NavMesh, Unity 6000.6.3f1. The spike code was in
`Assets/_Scratch/NavWorldSpike/` (an Editor test assembly, `[Explicit]` test) and is deleted. The funnel code is printed below.
Batch EditMode runs used: 3 (0 for discovery: the API was read by reflection outside Unity).

## Verdict

1. **Burst in the Editor: yes.** All path jobs ran compiled by Burst (a `[BurstDiscard]` check showed this; the log has no Burst errors). The Linux IL2CPP+Burst server build is **still to be proven, on the build box** (see check 5).
2. **Corners vs `CalculatePath`: yes on ordinary ground, not exact across links.** Same start and end points: 159 of 160 random pairs and 20 of 20 masked pairs match within 0.01 m. NavMeshLink pairs (roof gaps, links 1 m wide): only 14 of 40 match within 0.05 m and 22 of 40 within 0.1 m. The worst miss is 1.0 m, which is the full width of a link.
3. **`MapLocation` vs `SamplePosition`: same ground spot (XZ the same in every case), different height.** MapLocation gives the height of the NavMesh polygon and SamplePosition gives the finer detail-mesh height. MapLocation was higher every time, by 0.19 m on average and 0.52 m at most, so only 2 of about 150 points match within 0.05 m in 3D.
4. **Timing for 1,000 searches:** batched in 15 Burst jobs, 0.04 ms on the main thread and about 36 ms in total. 1,000 static `CalculatePath` calls take 257-323 ms, all on the main thread. Cost per search is about the same either way (243-331 µs in one Burst job, 257-323 µs static).
5. **Builds:** not run, by instruction. The job code uses nothing that Burst rejects. Linux IL2CPP+Burst and Android IL2CPP still need proving: "to prove on the build box".
6. **Pick: A (NavWorld) for monsters and NPCs, on one condition: the Linux proof passes before M5.4 lands.** By the plan's strict rule ("A if all yes") it is not all yes yet, because Linux is unproven and link corners differ. The two checks that decide monsters, (1) and (4), pass. Monsters do not need corners identical to `CalculatePath`. If the Linux proof fails, pick B. Option C for players later is **not** open as-is: link corners and click heights differ from the static calls.

## Check 1: does a Burst NavWorld path job run in the Editor?

- `NavWorld.GetDefaultWorld()` is valid in EditMode right after `EditorSceneManager.OpenScene(Zone01)`. The scene's 98 NavMeshLinks register themselves (they are `[ExecuteAlways]`). There is 1 agent type and only area 0 (Walkable).
- One `IJob` with `[BurstCompile]` does all of this: `MapLocation` (start and end), then `BeginFindPath`, then `ContinueFindPath(1024)` until it is no longer `InProgress`, then `EndFindPath`, then `GetResultFromFindPath` (the corridor of `NavNode`s), then `GetPortalPoints` for each pair of neighbouring nodes and `GetNodeType` (Polygon/Link), then the funnel. Every job ran under Burst (flag = 1 in all 15 batch jobs and in the single job). The log has no `BCxxxx` errors. The first job, including Burst's compile in the batch Editor, took 46-135 ms.
- Each job needs one `NavQueryBuffer(world, Allocator.Persistent, 4096)`. Making 15 took 0.5 ms. `world.AddDependency(handle)` was called after scheduling. The search never ran out of nodes (0 partial results); the default 1024 nodes was not tried.
- Unity's portal order matches Detour's "left/right" rule on polygons (11,382 agree, 0 disagree). The 42 that disagree are all link exits: `GetPortalPoints(link, poly)` gives the exit edge in the opposite order, so the funnel has to flip it to line up with the entry edge.

## Check 2: funnel corners vs `NavMesh.CalculatePath` corners

Pairs (fixed seed 5202): 160 random reachable pairs, 40 pairs aimed across NavMeshLinks (roof gaps; all 40 corridors really contain a link node), and 20 pairs with an area mask (no Jump area). Corridors average 52 nodes and paths run up to about 800 m, so most pairs cross the whole map.

| Pass (final funnel unless noted) | random (160) ≤0.01 / ≤0.05 / ≤0.1 m | link (40) | masked (20) |
|---|---|---|---|
| **C: same start/end as the static path's first/last corner** | **159 / 159 / 159** | **10 / 14 / 22** | **20 / 20 / 20** |
| D: as C, no colinear tolerance | 153 / 153 / 153 | 10 / 14 / 22 | 20 / 20 / 20 |
| E: plain funnel through links (no link handling) | 159 / 159 / 159 | 2 / 3 / 3 | 20 / 20 / 20 |
| run 1 funnel: link ends forced at their midpoint | 159 (same ends) | 0 / 0 / 1 | 20 |
| B: final funnel, raw random points as inputs | 109 / 109 / 110 (52 pairs unmapped, see below) | 10 / 14 / 22 | 13 of 13 mapped |

Whole map, pass C: 193 of 220 within 0.05 m and 201 of 220 within 0.1 m. Worst difference 1.0 m (a link). The corner count differs in 2 pairs.

Why the misses differ:
- **Links (the real gap).** Unity treats a wide NavMeshLink (1 m here) as a lane. The path crosses the link's entry edge and exit edge at points that depend on the corners before and after the link. My best model slides the corridor after the link so the exit edge lies straight ahead of the entry edge, one 3D link length on, then pulls the string through. That model matches some pairs to 3 mm. On others Unity behaves as if the link were shorter (one case fits a lane about 1.6 m long, not the 3.0 m 3D length), or crosses straight across the link without changing sideways position. All misses lie on the link's own two edges, between the link's two ends (≤ 1 m). The path length differs by 0.6 m at most. I could not get the exact rule within the spike's run budget.
- **Colinear points:** without a small tolerance, my funnel keeps a corner that lies on a straight line where Unity drops it (6 random pairs). With tolerance 1e-3 that is fixed.
- **1 random pair (#130)** goes along another corridor: NavWorld's A* found a path 3.1 m *shorter* than `CalculatePath`. Its funnel corners are right; the two searches simply chose different routes.
- **Endpoints (pass B):** when the job maps the raw points itself, the inner corners still match (0.0 m), but the first or last corner can sit 0.1-0.9 m apart. `CalculatePath` snaps its endpoints with its own search box, which is larger and taller. 52 of 220 raw points could not be mapped at all with extents (1,1,1). My test points (from `CalculateTriangulation`) sit 1.2-1.6 m below the polygon height in places, and `SamplePosition(r = 1)` misses them too. Extents (0.1, 2, 0.1) or (5,5,5) find all of them. **Use a taller box (y ≥ 2 m) when mapping monster feet.**
- **Area mask:** Zone01 has only area 0 (all 98 links are area 0 too), so the "no Jump" mask changed nothing. Both sides agree 20/20, but this does not prove area masking. A scene with a second area is needed for that.

## Check 3: `MapLocation` vs `NavMesh.SamplePosition` (click radius)

The click radius is `destinationSampleRadius` = **1 m** on the NGO player (`PointAndClickPlayer.cs:66`, value 1 in `Player.prefab`) and `SampleRadius` = **2 m** in the DOTS `NavMeshPathPlanner` (`PathPlanners.cs:117`). Both were tested with 200 points each: a point on the mesh plus a random offset of up to the radius in x, y and z. MapLocation used extents (r, r, r).

| radius | XZ same (≤0.05 m) | 3D same (≤0.05 m) | only SamplePosition hit | only MapLocation hit | both miss | height gap mean / max |
|---|---|---|---|---|---|---|
| 1 m | 148 / 148 | 2 | 0 | 1 | 51 | 0.19 / 0.52 m (MapLocation higher every time) |
| 2 m | 178 / 178 | 2 | 0 | 2 | 20 | 0.19 / 0.44 m (MapLocation higher every time) |

- Same spot on the ground every time (worst XZ difference 0.0000 m). The height differs because MapLocation returns the coarse polygon height, the same height `CalculatePath` corners use, while SamplePosition returns the detail-mesh height.
- The 1-2 extra MapLocation hits are box corners: the box reaches points that the 1 m sphere misses.
- For monsters this does not matter: they walk on corners, and both APIs give corners at polygon height. For players (option C) a click target would sit up to 0.5 m higher, so it would need a height fix (for example a physics ray down) before it could replace `SamplePosition`.

## Check 4: timing, 1,000 searches

The same 168 reachable pairs were reused to make up 1,000 searches. Each search includes MapLocation for both ends, the search and the funnel. 15 worker threads, one NavQueryBuffer per job, median of 3 runs after a warm-up, measured across 3 Unity runs.

| | main thread | total |
|---|---|---|
| 15 Burst jobs on workers | **0.03-0.04 ms** (schedule only) | **32-37 ms** (median 36.1) |
| 1 Burst job, 1 thread | ~0 | 243-331 ms (243-331 µs per search) |
| 1,000 static `CalculatePath` + `GetCornersNonAlloc` | **257-323 ms** | same |

These paths cross the whole map (52 nodes on average), so a monster's chase path will cost far less per search. The gain does not come from a cheaper search. It comes from moving the work off the main thread and spreading it over the workers, about 8x faster in wall-clock time.

## The funnel code used (the final pass; the spike's diagnostic counters are removed)

```csharp
[BurstCompile(CompileSynchronously = true)]
public struct PathJob : IJob
{
    public const int MaxPath = 2048, MaxCorners = 128;
    [ReadOnly] public NavWorld World;
    public NavQueryBuffer Buffer;                    // one per job: new NavQueryBuffer(world, Allocator.Persistent, 4096)
    public int AgentTypeId; public float3 Extents; public int Begin, Count; public float ColinearEps; // 1e-3
    [ReadOnly, NativeDisableContainerSafetyRestriction] public NativeArray<float3> Starts, Ends;
    [ReadOnly, NativeDisableContainerSafetyRestriction] public NativeArray<int> Masks;
    [NativeDisableContainerSafetyRestriction] public NativeArray<float3> Corners;   // MaxCorners per query
    [NativeDisableContainerSafetyRestriction] public NativeArray<int> CornerCounts;
    public NativeArray<NavNode> Path; public NativeArray<float3> L, R, UL, UR;      // scratch, own per job
    public NativeArray<byte> Kind, CSide; public NativeArray<int> CIdx;

    public void Execute() { for (int q = Begin; q < Begin + Count; q++) Run(q); }

    void Run(int q)
    {
        CornerCounts[q] = 0;
        int mask = Masks[q];
        NavLocation s = World.MapLocation(Starts[q], Extents, AgentTypeId, mask);
        NavLocation e = World.MapLocation(Ends[q], Extents, AgentTypeId, mask);
        if (!World.IsValid(s) || !World.IsValid(e)) return;
        NavQueryStatus st = World.BeginFindPath(Buffer, s, e, mask);
        while ((st & NavQueryStatus.InProgress) != 0) st = World.ContinueFindPath(Buffer, 1024, out _);
        if ((st & NavQueryStatus.Success) == 0) return;
        World.EndFindPath(Buffer, out int pathSize);
        int n = World.GetResultFromFindPath(Buffer, Path.Slice(0, math.min(pathSize, MaxPath)));
        if (n == 0) return;
        // portals: 0 = start point, k = between Path[k-1] and Path[k], n = end point
        L[0] = s.position; R[0] = s.position;
        for (int k = 1; k < n; k++) { World.GetPortalPoints(Path[k - 1], Path[k], out Vector3 l, out Vector3 r); L[k] = l; R[k] = r; }
        L[n] = e.position; R[n] = e.position;
        int cc = 0;
        RunUnfolded(n, q * MaxCorners, ref cc);
        CornerCounts[q] = cc;
    }

    // A NavMeshLink is a lane: the corridor after a link is slid (XZ) so the exit edge lies straight ahead of the entry edge at
    // the link's 3D length; one funnel runs over the unfolded strip; where a straight stretch crosses a link's entry and exit
    // edge becomes a corner. (Matches Unity on 14/40 link pairs within 5 cm, 22/40 within 10 cm; exact on polygons.)
    void RunUnfolded(int n, int cBase, ref int cc)
    {
        for (int k = 0; k <= n; k++) Kind[k] = 0;
        for (int k = 1; k + 1 < n; k++)
        {
            if (World.GetNodeType(Path[k]) != NavNodeType.Link) continue;
            Kind[k] = 1; Kind[k + 1] = 2;
            float3 me = (L[k] + R[k]) * 0.5f, mx = (L[k + 1] + R[k + 1]) * 0.5f, dir = mx - me;
            if (math.lengthsq(dir.xz) < 1e-8f) dir = (L[k + 2] + R[k + 2]) * 0.5f - (L[k - 1] + R[k - 1]) * 0.5f;
            if (Cross2(dir, L[k] - me) < 0) { float3 t = L[k]; L[k] = R[k]; R[k] = t; }          // Detour: left has cross > 0
            float same = math.distance(L[k + 1].xz, L[k].xz) + math.distance(R[k + 1].xz, R[k].xz);
            float swap = math.distance(L[k + 1].xz, R[k].xz) + math.distance(R[k + 1].xz, L[k].xz);
            if (swap < same) { float3 t = L[k + 1]; L[k + 1] = R[k + 1]; R[k + 1] = t; }          // exit edge comes reversed
        }
        float2 off = float2.zero;
        for (int k = 0; k <= n; k++)
        {
            if (Kind[k] == 2)
            {
                float3 me = (L[k - 1] + R[k - 1]) * 0.5f, mx = (L[k] + R[k]) * 0.5f;
                float2 d = mx.xz - me.xz; float len = math.length(mx - me);
                d = math.lengthsq(d) > 1e-8f ? math.normalize(d) : float2.zero;
                off = me.xz + off + d * len - mx.xz;
            }
            UL[k] = new float3(L[k].x + off.x, 0, L[k].z + off.y);
            UR[k] = new float3(R[k].x + off.x, 0, R[k].z + off.y);
        }
        // simple stupid funnel (Mononen / Detour findStraightPath) over the unfolded portals -> (portal index, side)
        int m = 0; CIdx[m] = 0; CSide[m] = 0; m++;
        float3 apex = UL[0], pl = UL[0], pr = UR[0];
        int apexIndex = 0, leftIndex = 0, rightIndex = 0;
        for (int i = 1; i <= n; i++)
        {
            float3 left = UL[i], right = UR[i];
            if (TriArea2D(apex, pr, right) <= 0f)
            {
                if (Eq(apex, pr) || TriArea2D(apex, pl, right) > -ColinearEps) { pr = right; rightIndex = i; }
                else { apex = pl; apexIndex = leftIndex; if (m < MaxCorners) { CIdx[m] = leftIndex; CSide[m] = 0; m++; }
                       pl = apex; pr = apex; rightIndex = apexIndex; i = apexIndex; continue; }
            }
            if (TriArea2D(apex, pl, left) >= 0f)
            {
                if (Eq(apex, pl) || TriArea2D(apex, pr, left) < ColinearEps) { pl = left; leftIndex = i; }
                else { apex = pr; apexIndex = rightIndex; if (m < MaxCorners) { CIdx[m] = rightIndex; CSide[m] = 1; m++; }
                       pl = apex; pr = apex; leftIndex = apexIndex; i = apexIndex; continue; }
            }
        }
        if (m < MaxCorners) { CIdx[m] = n; CSide[m] = 0; m++; }
        // back to real positions, adding the link edge crossings
        for (int j = 0; j < m; j++)
        {
            int ia = CIdx[j];
            Add(cBase, ref cc, CSide[j] == 0 ? L[ia] : R[ia]);
            if (j + 1 >= m) break;
            int ib = CIdx[j + 1];
            float3 pa = CSide[j] == 0 ? UL[ia] : UR[ia], pb = CSide[j + 1] == 0 ? UL[ib] : UR[ib];
            for (int k = ia; k < ib; k++)
            {
                if (Kind[k] != 1) continue;
                if (k != ia) Add(cBase, ref cc, EdgeCrossing(pa, pb, k));
                if (k + 1 != ib) Add(cBase, ref cc, EdgeCrossing(pa, pb, k + 1));
            }
        }
    }

    float3 EdgeCrossing(float3 p, float3 q, int k)
    {
        float3 r = q - p, e = UR[k] - UL[k];
        float den = Cross2(e, r);
        float t = math.abs(den) < 1e-9f ? 0.5f : Cross2(p - UL[k], r) / den;
        return math.lerp(L[k], R[k], math.saturate(t));
    }
    void Add(int cBase, ref int cc, float3 p)
    {
        if (cc > 0 && math.distancesq(Corners[cBase + cc - 1], p) < 1e-8f) return;
        if (cc < MaxCorners) { Corners[cBase + cc] = p; cc++; }
    }
    static float Cross2(float3 u, float3 v) => u.x * v.z - u.z * v.x;
    static float TriArea2D(float3 a, float3 b, float3 c) => (c.x - a.x) * (b.z - a.z) - (b.x - a.x) * (c.z - a.z); // dtTriArea2D
    static bool Eq(float3 a, float3 b) => math.distancesq(a, b) < 1e-12f;
}
```
